# PaddleOCR-VL 1.6 local feasibility and two-document test

**Status, 12 October 2026:** research and host inspection only. No model weights were downloaded, no inference ran, and product runtime was not changed. A local fit on the 8 GiB GPU remains unmeasured.

## Recommendation

Try the **complete PaddleOCR-VL 1.6 pipeline** in an isolated native Windows environment, with PP-DocLayoutV3 on CPU and the official 1.6 GGUF VLM in the already available CUDA-enabled `llama.cpp` server. Freeze the package/model revisions and capture actual memory before scoring. This is a two-public-document engineering diagnostic, not an automatic product dependency. Retain the current parser control until this candidate shows linked-row and evidence gains for an acceptable incremental cost.

The [official pipeline guide](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md) says the full route detects layout regions, orders and crops them, recognizes each region with the VLM, then assembles page results. Running the 0.9B VLM alone is *not* the full page parser. The [official 1.6 pipeline configuration](https://github.com/PaddlePaddle/PaddleX/blob/release/3.7/paddlex/configs/pipelines/PaddleOCR-VL-1.6.yaml) names `PP-DocLayoutV3` and `PaddleOCR-VL-1.6-0.9B`; layout detection defaults on while orientation, unwarping, chart and seal modules are off. The guide documents a `llama-cpp-server` backend for the VLM and says the client still runs layout analysis locally.

Both are from the pinned [Google VRDU cohort](VRDU_2000_NO_MODEL_V6.md) at creator commit `04a4df7ac5cc694e51c48115c03fe428f0e240cc`; the listed source SHA-256 values were independently rehashed locally. The selection is deliberately diagnostic: one multi-page native-text table and one single-page scan. It is too small and too targeted for a population estimate.

The VRDU row gold gives per-column value strings and row ordinals, but **not adjudicated pixel boxes for individual cells**. Do not equate a table HTML string or a matching value anywhere on the page with a correctly grounded cell.

## Bounded diagnostic contract

1. Render all four source pages once with pinned `pypdfium2==5.14.0` at scale 2 (144 DPI), preserving page rotation. Save PNG SHA-256, original PDF SHA-256, 0-based source page, width/height and renderer receipt. Supply the same PNG bytes to PaddleOCR-VL and each table comparator; map the image result back to the PDF page in the wrapper because image input has no inherent PDF `page_index`.
2. In an isolated environment, run `PaddleOCRVL(pipeline_version="v1.6", device="cpu", use_layout_detection=True, use_doc_orientation_classify=False, use_doc_unwarping=False, use_chart_recognition=False, vl_rec_backend="llama-cpp-server", vl_rec_server_url="http://127.0.0.1:<test-port>/v1", vl_rec_max_concurrency=1)`. Serve only the pinned official GGUF+projector on localhost at temperature zero. Freeze model, framework, server, context and token caps; run pages sequentially. If native CPU layout or GGUF loading fails, report the precise stage and stop rather than substitute an unpinned backend. A separate CPU-only full Paddle route is a fallback feasibility test, with its potentially high latency explicitly measured.
3. Save raw per-page JSON, Markdown/HTML and overlays, plus cold/warm wall time, peak host RSS and sampled GPU VRAM. The [official output contract](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md#22-python-script-integration) includes page dimensions, `parsing_res_list`, each block's `block_bbox`, label/content/order, and table HTML export. Check that table blocks align with the original page image and that page/reading order is stable. The guide documents `layout_shape_mode` (`rect`, `quad`, `poly`, `auto`); retain raw geometry and the chosen mode.
4. Before looking at candidate output, mark table-region polygons and a small fixed set of cell centers/strings on these four page PNGs. Score table-region IoU, whether each marked cell center lies in the right table region, exact positive cell-value recall by VRDU row and column, and complete annotated row linkage. Count missing/extra HTML rows, column shifts, repeated-text mislinks, generation truncation and malformed HTML. Keep native and scanned results separate. The manual cell centers test table-region mapping; they **do not** create a per-cell output box that the model did not provide.
5. Require all four pages to return explicit success/failure without OOM or silent page loss. Do not promote to production unless a later source-locked, larger comparison improves correct linked rows and evidence while meeting measured latency/review cost. Treat `block_bbox` as region provenance only: the documented result does not establish pixel boxes for generated HTML cells. Per-cell source evidence would require a separately tested OCR-to-cell alignment or a model with cell geometry.

The direct Transformers example on the official model card is element recognition/text spotting and does not provide the whole layout pipeline. The model's published benchmark score is a reason to test, not a claim that it will fix this product's schema or row accuracy.
