# ICORE transport follow-up for the six-public-PDF pilot

The [six-public-PDF pilot](ICORE_VRDU_SIX_PILOT.json) attempted six chat requests with `innobot-luna-6` through the OpenAI-compatible `/chat/completions` path, with SDK retries disabled and a 90-second request timeout. One schema call returned a valid HTTP response with reported token usage. The other five returned `APIConnectionError` with no HTTP status: two after 76.923 and 81.054 seconds, then three after 1.771, 1.297, and 3.660 milliseconds. The pilot did not save the underlying exception cause or a safe network trace. These are transport failures, not observed HTTP 429, HTTP 401, schema rejection, or a measured extraction-quality result.

On 2026-10-11 UTC / 2026-10-12 Asia/Colombo, this host resolved `icore.innobothealth.us` to two addresses in 10.072 seconds and completed a verified TLS 1.3 handshake in 1.858 seconds. One additional **synthetic** chat request through the same base URL, credential class, OpenAI SDK client, and `innobot-luna-6` model succeeded with `finish_reason=stop` in 1.639 seconds. The response reported 20 prompt tokens and 9 completion tokens. The request used a 30-second timeout, `max_tokens=12`, and `max_retries=0`; neither its response content nor the credential was logged. No VRDU or private document text was sent in the follow-up. Pricing was unavailable, so this request's settled charge is unknown.

**Diagnosis:** a permanently incorrect client path, credential, or model ID is contradicted by successful calls before and after the failed pilot. DNS and TLS work now. The old `APIConnectionError` type alone cannot distinguish a remote socket closure, service instability, DNS/TLS failure during those requests, or an intervening network problem. The two long failures suggest time spent waiting for a connection or response; the three near-immediate failures suggest a different failure mode or changed network/service state. This timing is diagnostic, not proof of a particular cause. No HTTP rate-limit response was seen, so rate limiting is also unproven. The pilot remains a failed connectivity-limited extraction test.

The bounded next diagnostic is to run **at most two synthetic chat calls** only when a future endpoint failure recurs, while recording sanitized exception class chains (`__cause__` types, never messages), phase, elapsed time, HTTP status if present, SDK retry count, and a same-time DNS/TLS check. The current `idpo.product_auto.provider` classifies some transport causes without persisting exception strings; the old pilot lacked that category. Do not retry billable requests automatically until duplicate billing behavior and provider idempotency are verified. No production extraction or routing change is justified by this follow-up.
