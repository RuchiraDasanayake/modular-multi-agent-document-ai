# PP-TableMagic v2 on the ad-buy table lock: read-only feasibility

**Decision, 12 October 2026:** a guarded **CPU-only development pilot is feasible to attempt on C:** after model acquisition is separately authorized and source-locked. There has been **no model download, pipeline construction, PDF inference, or score** in this review. The earlier PaddleOCR-VL 1.6 result remains **14/219** complete exact-cell rows and **0/219** exact-multiset rows; PP-TableMagic has no measured result yet. Neither candidate is approved for product integration or the 2,000-document gate.

## Candidate and exact installed defaults

The [official v3.7.0 tutorial](https://github.com/PaddlePaddle/PaddleOCR/blob/v3.7.0/docs/version3.x/pipeline_usage/table_recognition_v2.en.md) describes `TableRecognitionPipelineV2` / PP-TableMagic as layout detection, OCR, table classification, wired/wireless structure recognition and wired/wireless cell detection, with optional document orientation and unwarping. It accepts individual PDF paths and emits one result per page with `page_index`, `layout_det_res`, `overall_ocr_res`, and `table_res_list`. The published result includes `pred_html`, `cell_box_list` and `table_ocr_pred` with OCR text/polygons/boxes. The local [PaddleX 3.7.2 pipeline configuration](https://github.com/PaddlePaddle/PaddleX/blob/v3.7.2/paddlex/configs/pipelines/table_recognition_v2.yaml) enables layout, OCR, document orientation and unwarping and names **ten distinct default models**. Its installed SHA256 is `7ae76188079fed0e4cadc3ea5570ca85b506b7144b2cf0c3adbad84eb8d0f4a0`. Table orientation reuses the same `PP-LCNet_x1_0_doc_ori` asset, though it may create another predictor instance.

## Host and output feasibility

The isolated existing Windows Python 3.11 environment imports `TableRecognitionPipelineV2` with PaddlePaddle CPU 3.3.0, PaddleOCR 3.7.0 and PaddleX 3.7.2. `paddle.get_device()` reports `cpu`. This proves import and dependency availability, **not** ten-model startup or conversion. The prior PaddleOCR-VL pipeline used this environment successfully with a CPU layout model, but its memory use does not bound PP-TableMagic's ten-model memory use.

At inspection, host available RAM was **8.77 GiB** of 23.91 GiB; C: free **9.23 GiB**, E: free **3.71 GiB**. Preserving the earlier C: 4 GiB / E: 2 GiB floors leaves 5.23 GiB / 1.71 GiB usable. Full assets alone consume 1.282 GiB before download staging, raster buffers, caches and result files. **E: is no-go for staging.** C: has room for one verified local model set with temporary headroom; full CPU model loading remains an unmeasured memory risk. Use C: for verified weights and E: for small raw receipts only, subject to fresh guards.

The [installed result serializer](https://github.com/PaddlePaddle/PaddleX/blob/v3.7.2/paddlex/inference/pipelines/table_recognition/result.py) preserves each page's `table_res_list[].cell_box_list`, `pred_html` and `table_ocr_pred`, plus overall OCR and layout detections. The local `result.py` SHA256 is `7e0ded5597ee4a4713605c7e72d5a1de3c84fbb64662e7560659909d007861d3`; `pipeline_v2.py` SHA256 is `9285995eb1cb7f79547a7abca8abe74aeb8b29471925fab2b0ef383c9082779c3`. This is stronger evidence *potential* than PaddleOCR-VL's table-region-only output. The JSON serializer omits the runtime table's `table_region_id` and does **not** explicitly serialize an HTML-cell-to-box ID or OCR-token-to-HTML-cell ID. A later worker should separately retain the real runtime region ID with each result and verify its layout correspondence. Cell boxes are detected regions; linking a particular HTML value to one requires a measured alignment check. With unwarping, box coordinates may refer to the processed raster rather than the original PDF page. Do not claim grounded values from box availability alone.

## Conditional, source-locked challenge protocol

1. **Freeze before acquisition or inference.** Reuse exactly [`vrdu_ad_buy_table12.jsonl`](../../product_eval/fixtures/vrdu_ad_buy_table12.jsonl), SHA256 `b843d48146a60f02bb206900ee06d446eb82ba484a3781c291235864b5230d2d`, cohort hash `98f4fcbd6521594304da3a80104362cf89174c87c27ed08ce90a1158fef4bc90`, gold hash `8a631bffbf439ccc8376f84cbf7d4af25c86d35c0ccc7996ce3b23e6085138bf`. Keep all **12 PDFs, 28 pages, 219 linked rows and 808 cells** in the denominator, including two image-only PDFs. Pin every local model file hash, package closure, pipeline YAML, scorer, runner, config and source PDF before conversion. Do not let gold into prompts/configuration or tune on these 12 sources.
2. **Use the full table pipeline, with an explicit source-coordinate profile.** Keep layout detection, OCR, table classification, both wired/wireless structure models, both cell detectors, and default table orientation on. Predeclare `use_doc_orientation_classify=False` and `use_doc_unwarping=False` for this upright-PDF development set; the table orientation model still uses `PP-LCNet_x1_0_doc_ori`. This is **nine distinct assets**, about 1,344,345,025 bytes all files. It leaves PDF page raster coordinates interpretable without nonlinear unwarping; any rotated-page failure remains counted. Do not substitute a VLM-only or OCR-only route. Run `device="cpu"`, local `paddle_static`, one document process at a time and no cloud calls.
3. **Guard a single PDF smoke, then decide.** Verify source/model hashes and fresh free space; reserve C: at least 4 GiB and E: at least 2 GiB at all times. Require at least 6 GiB available host RAM before startup, then at least 3 GiB during the smoke; stop if process-tree RSS exceeds 8 GiB, if startup exceeds 180 seconds, or if the first three-page PDF exceeds 600 seconds. Require page-indexed saved JSON with `model_settings.use_layout_detection=true`, at least one actual table `pred_html` containing `<table>/<tr>/<td>`, finite positive `cell_box_list` rectangles inside page bounds, table-region boxes and OCR text boxes in a consistent raster coordinate frame. Save failures rather than changing model choices after seeing output. Only then allow the other eleven PDFs, with an 8-minute per-PDF and one-hour whole-run cap and the same resource floors. Ordinary PDF failures stay in the denominator.
4. **Score table parsing and evidence separately.** Feed only `table_res_list[].pred_html` parsed HTML rows/cells to the frozen `score_tables` implementation. Report the identical one-to-one complete exact-cell row measure that allowed extra parser cells in the PaddleOCR-VL **14/219** result; also exact cells, substring presence and strict entire-row multiset. Do not score `overall_ocr_res` prose or Markdown as table rows. Retain each detected `cell_box_list`, `table_ocr_pred` text/boxes, layout table box, page dimensions and page index in raw JSON. Independently audit box geometry, HTML physical-cell counts (respecting spans), text-to-OCR match and spatial overlap before asserting per-cell source evidence. Never fabricate a cell box or assume list order proves alignment.
5. **Decision.** A smoke failure is a runtime **no-go**. A completed 12-PDF run may justify wider development only if its paired complete-row score materially exceeds 14/219, strict rows are nonzero, and an independently checked cell-to-source alignment is valid. A reasonable predeclared challenge threshold is at least **30/219** complete rows and at least **1/219** strict row, plus valid source coordinates for matched cells; meeting it still does **not** justify product promotion. Product decisions require a disjoint, diverse benchmark, field-attributed accuracy and HITL evidence, cost/throughput measurements, and only then the 2,000-document gate.

**Current status:** read-only feasibility only. No PP-TableMagic model files were downloaded, no pipeline was instantiated, no PDF was converted, and no score was changed.
