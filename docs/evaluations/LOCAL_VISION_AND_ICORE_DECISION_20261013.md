# Vision and extraction candidate decision, 13 October 2026

**Recommendation:** Keep the current review-first product path, approved versioned recipes for repeat document families, and source-backed native table proposals. Do not add the tested Qwen3-VL-2B profile or ICORE Sonnet 5 vision as an automatic extractor. The next candidate should pair reliable parser/header structure with a reviewed or independently evaluated semantic schema, then verify every linked row and source cell before release. A more capable model can be a bounded fallback only after a source-disjoint public-document quality and cost trial.

This is a decision from measured development evidence, not a claim that the current system meets the goal. The main product commit `de289de` completed a mixed **2,000-distinct-raw-source** no-model gate: 798 CORD receipts, 897 VRDU registration PDFs and 305 VRDU ad-buy PDFs, with all sources and result receipts verified, zero source failures and zero auto releases. Its exact schema F1 was 3.3749695%, and it proposed **zero linked cells and rows** against 24,738 annotated linked cells and 6,541 combined rows. Its CORD positive-only exact proposed score was 0/2,654 scalars, 0/6,066 linked cells and 0/2,076 eligible complete rows. These three families do not establish arbitrary-document quality or review cost. See the [sealed mixed gate](MIXED_VRDU_CORD_TRAIN_2000_NO_MODEL_RESULT_20261013.md).

The local model result identifies a concrete schema-discovery failure under its pinned prompt and output cap. The ICORE result identifies an output-contract failure on an easy synthetic image, while suggesting that its image transport works. Neither justifies replacing OCR, adding another agent loop or turning on automatic release. In earlier paired CORD development work, RapidOCR PP-OCRv6 made far more annotated text visible than Tesseract but the unchanged extractor still mapped zero exact receipt fields or linked rows with either engine; OCR choice alone does not resolve schema meaning. The conditional NuExtract3 reference-schema arm found 24/43 complete rows on six development PDFs, with 21 from one source and no verified source boxes; it remains a hypothesis for reviewed recurring schemas, not a promoted extractor.

Use the existing [target architecture](../PRODUCTIZATION_PLAN.md): authenticated API and immutable artifacts; bounded CPU parsing and optional GPU/model workers; versioned schema/recipe; typed value and source verification; explicit abstention and owner-scoped human review; durable job state in PostgreSQL with a bounded Redis-backed queue only after the live container path is demonstrated. A separate vector database, autonomous agent swarm or extra microservice has no measured gain here. Keep components behind a common parsed-document, result and evidence contract so a better open-source parser can replace one stage without rewriting review or scoring.

The next quality gate needs rights-cleared, source-disjoint real documents across formats and families, including linked tables and source locations. The creator's [ExtractBench](https://github.com/run-llama/ExtractBench) is a conditional external PDF comparator with 370 cases and supplied schemas; score its supplied-schema value arm separately from our automatic-schema arm, and audit source rights and overlaps before admission. Any newly integrated extraction implementation must then process **at least 2,000 distinct original sources end to end**, with every failure, review, evidence, latency and cost denominator retained. Do not call a model, database or parser change cheaper until cost per correctly released document is measured.
