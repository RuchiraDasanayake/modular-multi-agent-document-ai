# RapidOCR PP-OCRv6 scan-page pilot (12 October 2026)

**Decision:** PP-OCRv6 small is a credible *selective OCR candidate* for scanned pages, not a replacement or a product-quality extraction result. On 30 preselected public VRDU scan pages, it exposed more page-local gold scalar values than the completed v5 Tesseract output, while requiring more time and memory per page in this CPU configuration. The gain is in OCR text availability; no schema, linked-row, typed-value, source-evidence, review-time, or end-to-end accuracy improvement has been demonstrated.

Selection used the frozen VRDU development cohort and gold: sort by source SHA within each of the two families; take the first 15 distinct documents with a v5 Tesseract page and at least one non-null *scalar* gold value carrying page-local evidence. If a document had multiple eligible scan pages, take the one with most such targets, then earliest page. This deliberately favors scoreable scanned pages and is **not** a representative random sample of all documents or all scans. The 30 sources are distinct, 15 ad-buy and 15 registration.

Both engines received the exact page PNGs rendered and retained by the [v5 product gate](VRDU_2000_NO_MODEL_V5.md), rather than separately rasterizing PDFs. The comparison uses v5's actual selected Tesseract text for coverage. For latency and child-process memory, it reruns **one** pinned Tesseract `--oem 3 --psm 6` pass against the same PNG. That direct pass is a timing control; its output is not substituted for the v5 adaptive-retry text. The v5 production path can render, rotate, preprocess, and retry multiple candidates and has document-level timings, so the per-page direct timings below are not an end-to-end product latency claim.

## Measured result

"Value present" means the gold scalar string, after Unicode NFKC, case folding, and punctuation/whitespace normalization, appears in the OCR page text. It is a **recall-like transcription proxy**, not a field extraction, precision, evidence-correctness, or CER/WER score. The gold page text is not a certified full-page transcription, and reading order/layout differ; therefore CER/WER would be misleading here. Null values, `array[object]` fields, and linked rows are excluded from this proxy.

| Family | Pages | Page-local scalar targets | v5 Tesseract text present | RapidOCR text present | Paired changes (Rapid only / v5 only) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Ad-buy | 15 | 111 | 82 (73.9%) | 93 (83.8%) | 14 / 3 |
| Registration | 15 | 35 | 25 (71.4%) | 28 (80.0%) | 3 / 0 |
| **Combined** | **30** | **146** | **107 (73.3%)** | **121 (82.9%)** | **17 / 3** |

Net difference is **+14/146 targets (+9.59 percentage points)**. Eight pages improved, two worsened, and 20 tied by target count. The three exact-string losses include an agency string, an address, and a product string; the 17 gains include contract numbers, flight dates, gross amounts, products, and three registration signer/date fields. Manual text inspection shows that the address's two lines are both in RapidOCR output but separated by reading order; the agency gold string is truncated at `Washil` while RapidOCR has a longer spelling; the product lacks a separating space in RapidOCR. These are failures of the strict presence proxy, not three adjudicated transcription errors. A source-stratified 10,000-resample paired bootstrap, seed `20261012`, gives +2.24 to +17.42 percentage points for this fixed selection. That interval describes uncertainty from reweighting these selected sources only; it does not establish generalization to arbitrary documents.

| Operational measure | RapidOCR PP-OCRv6 small | Direct single-pass Tesseract timing control |
| --- | ---: | ---: |
| Successful pages / explicit failures | 30 / 0 | 30 / 0 |
| Warm per-page latency p50 / p95 | 5.50 / 9.00 s | 1.59 / 2.92 s |
| Peak sampled process RSS | 764 MiB | 139 MiB |
| Page polygons within original PNG bounds | 2,617 / 2,617 | Not captured in v5 text sidecar |

The RapidOCR warm-up took 2.33 s and is excluded from per-page times. Memory was sampled every 20 ms during each call; short peaks may be missed. The RapidOCR RSS includes the Python/NumPy/ONNX process; Tesseract RSS is its child executable and is not a like-for-like total service memory comparison. A Qwen3-VL pilot could overlap on the same host during this run, so these CPU latencies need an isolated repeat before sizing a deployment. The OCR adapter itself used no GPU inference provider; incremental VRAM was not measured. CPU energy, reviewer labor, and local hardware cost were not priced; API spend was zero.

The returned 2,617 polygons mapped within the original image bounds, which is a coordinate sanity check. It does **not** validate that an OCR line identifies the right field, that evidence quotes correspond to pixel regions, or that ad-buy table cells can be assigned to their correct rows. Current `product_auto` serializes only page text and checks quote offsets against that text; it drops OCR geometry. To use these polygons as inspectable evidence, a versioned parsed-page adapter must retain each line's original-pixel polygon, page size/rotation and deterministic start/end offsets into the exact page text sent to the model. Preserve raw engine order and a separate reading-order index. Do not infer table row IDs from the flat OCR line sequence; a cell/row parser and an adjudicated row-link test are required. The current extraction system's [v5 2,000-document gate](VRDU_2000_NO_MODEL_V5.md) still had zero accepted-value F1 and zero proposed linked cells/rows. This OCR pilot cannot repair those deficits by itself.

An exploratory routing calculation on the same 30 pages found that applying RapidOCR only where v5's **final** Tesseract confidence was below 80 would send 10 pages and recover 11 values while losing two, a net +9 targets. That threshold was examined **after** viewing pilot outcomes, and production would need to act on first-pass signals instead of the final v5 confidence. It is a candidate for an independent, predeclared 50-document test, not a tuned production rule. A sensible gated fallback would consider first-pass no text, timeout/partial failure, low confidence, and independently detected scan/table risk, then keep both raw outputs and defer to review when they disagree on a critical field. The trigger must improve cost per correctly reviewed document and retain exact source evidence on a holdout before release.

## Windows GPU feasibility and next cost comparison (read-only plan)

**Assessment, 12 October 2026:** the *same ONNX weights* have an official Windows NVIDIA route through [ONNX Runtime's CUDA execution provider](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html). This host reports an RTX 3060 Ti (8,192 MiB, compute capability 8.6), driver 610.88, and CUDA UMD 13.3. Those facts make an isolated trial plausible; they do **not** establish that the required CUDA/cuDNN DLLs are present, that all three models load on the GPU, that their operators execute there, or that 8 GiB is sufficient alongside other workers. No GPU package, weights, or inference were installed/run for this assessment.

After the active 2,000-document gate, compare CPU ORT 1.23.2 and GPU ORT-GPU 1.23.2 **on the same frozen 30 page PNGs**, with the same RapidOCR 3.10.0 preprocessing, three model hashes and output normalization. Record session providers **and operator-level provider placement** with [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html); reject a silent CPU fallback. Record cold load, warm p50/p95 page latency, total sequential and bounded-batch throughput, peak host RSS and incremental VRAM, failures, polygons, text order, the 146-value presence proxy, and any changed/lost values. Measure with no competing GPU job and state the batch size, idle power and energy method before estimating local cost per page and cost per additional correctly exposed value. The existing direct Tesseract timing is only a single-pass control, so compare GPU against both the exact CPU RapidOCR pipeline and the separately measured production Tesseract path. [RapidOCR cautions that ONNX GPU may be slower than CPU for dynamic OCR image shapes](https://rapidai.github.io/RapidOCRDocs/main/en/faq/faq/); speed and economics remain empirical, and value presence still is not extraction quality.
