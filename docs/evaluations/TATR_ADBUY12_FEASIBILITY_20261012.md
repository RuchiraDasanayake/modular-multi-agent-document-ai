# Table Transformer feasibility on the frozen VRDU ad-buy table slice

12 October 2026. **Decision: conditional go for a guarded, parser-only comparator; no go for product integration.** Microsoft Table Transformer (TATR) offers cell boxes and row/column membership at a small checkpoint size, but there is no result on these 12 PDFs yet. Its visual model does not recognize cell text: a trustworthy, image-aligned **word-box** feed is a prerequisite. The current product does not retain one. Do not infer a quality gain from its PubTables/FinTabNet training results.

## What the established pipeline actually supplies

- The [official inference guide](https://github.com/microsoft/table-transformer/blob/main/docs/INFERENCE.md) has separate page table detection and cropped-table structure recognition, or a combined extract mode. It takes a `PIL.Image` and optionally reading-order tokens shaped `{"bbox": [xmin, ymin, xmax, ymax], "text": "word"}` in **image pixels**. Without tokens it can return geometry but cannot put text in HTML/CSV. Its cell-list output retains more information than HTML/CSV, including cell boxes.
- The [official postprocessor](https://github.com/microsoft/table-transformer/blob/main/src/inference.py) derives cells from row/column intersections and spanning-cell detections. Cells carry `bbox`, `row_nums`, `column_nums`, header flags, assigned spans, and `cell text` from the supplied tokens. Cropping shifts the word boxes into crop coordinates and handles rotated tables. A box is therefore model-derived geometry; correct text and source identity still depend on the upstream words and coordinate transform.
- The [v1.1-All model card by the authors](https://huggingface.co/bsmock/TATR-v1.1-All) says these weights work best with **tight table crops, at most about 5 pixels of padding**. The generic inference-guide example uses 20 pixels; the proposed v1.1 profile below fixes 5 pixels and records every detected crop. No gold-derived crop is allowed.

## Local token and evidence fit

The [product intake](../../idpo/agents/intake.py) stores native PDF **page text and rotation, not word boxes**; the [product workflow](../../idpo/product_auto/workflow.py) passes page text to its evidence resolver. The isolated [pdfplumber diagnostic](../../product_eval/pdfplumber_table_diagnostic.py) can produce native word boxes; a read-only check on the first selected native page found 501 words. The same check on a zero-native-text scan found none. The existing [RapidOCR receipt path](../../product_eval/cord_page_ocr_diagnostic.py) exposes image-pixel **line quadrilaterals** with text and confidence. Those are useful OCR regions, but a line can cross several cells and is not the required word-token feed. Directly reusing line polygons as words would be an unvalidated approximation. A future scan arm needs a verified OCR word-box source or a validated segmentation bridge, with separate OCR error receipts. Native PDF word boxes likewise need a tested PDF-to-rendered-image transform, including page rotation and crop offsets.

The fixed set has **12 PDFs, 28 pages, 219 gold linked rows, 808 nonempty linked cells**; two image-only PDFs contribute 32 rows/84 cells. Every source, failed parse, missed table, and token failure stays in the denominator. The hashes and denominators were rechecked read-only for this note.
2. Use one fixed, source-only path: pinned PDFium at 300 DPI, one page at a time; native PDF word boxes where available, and a predeclared OCR **word-box** path for the two scans. Preserve source page, render size/rotation, token text, native or OCR provenance, pixel box, and reading order. Validate coordinate alignment on a native page and scan *before* scoring. A missing word-box path is a no-go for text scoring on those pages, not a license to drop their gold rows. Do not use gold labels or boxes for table cropping, token assignment, tuning, or repair.
3. Run the PubTables detection checkpoint plus **v1.1-All** recognition with 5-pixel crop padding, the [official 0.5 class thresholds and 800/1000-pixel detector/structure resize](https://github.com/microsoft/table-transformer/blob/main/src/inference.py), CPU, one document per process, four threads, at most 20 pages/2 MB/360 seconds per document, and no cloud call. Start with a one-page resource smoke after Paddle finishes. Reuse the [MinerU comparator guard](../../product_eval/mineru_table_diagnostic.py): smoke below 6 GiB process-tree RSS with more than 3 GiB host RAM available, then full-run ceiling 8 GiB RSS with at least 2 GiB host RAM available. Save checkpoint/runtime hashes, every page's table detections and crop transforms, raw **cell-list** output (not only HTML/CSV), OCR/token receipts, failures, wall time, and sampled process-tree peak RSS. Stop if the resource guard fails; report the failure without changing the cohort. Pub and Fin arms may then reuse the identical page renders/tokens and keep separate results.
4. Feed TATR's predicted `cell text` strings and rows keyed by `row_nums` to the existing [unlabeled table scorer](../../product_eval/docling_table_diagnostic.py): `gold_linked_rows`, `normalize`, and `score_tables`. Keep its NFKC/casefold/whitespace-only normalization, one-to-one exact cell string counting, one parser row per gold row, and `complete_rows_exact_cells_one_to_one` as the primary **/219** measure. Report exact cells **/808**, substring presence, within-row pairs, entire-row exact multiset, native **/187** versus scan **/32** rows, table/row/cell counts, and per-document failures. Spanning cells belong to their starting row, matching the prior comparison. Record the share of cells with page and finite box, token assignment, OCR source, p50/p95 wall time and peak RSS. VRDU gold has no cell-region labels, so box receipt coverage is **not** box accuracy; audit fixed overlays separately.
5. Compare the paired result with the existing [Docling/pdfplumber](VRDU_ADBUY12_TABLE_PARSER_COMPARISON_20261012.md) and [MinerU Basic](MINERU_4_BASIC_ADBUY12_RESULT_20261012.md) controls: Docling 3/219 exact complete rows and 279/808 exact cells, pdfplumber `text` 4/219 and 237/808, MinerU Basic 6/219 and 211/808. Do not promote a marginal row gain or a geometry-only success. Any promising result still needs correct business field attribution, source-grounded review, a disjoint mixed-format holdout, and a new 2,000-distinct-source product gate after implementation.

**Limit:** This note is a source and local-code feasibility audit. No TATR checkpoint was downloaded, loaded, timed, or scored here. Its quality, RAM peak, CPU throughput, and cost per correct row on VRDU remain unknown.
