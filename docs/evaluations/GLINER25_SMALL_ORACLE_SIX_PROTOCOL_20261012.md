# GLiNER2.5 Small local oracle-schema diagnostic protocol

**Status: frozen before weight acquisition and inference.** This is a CPU-only comparison of supplied-schema text extraction on the exact six scored development sources from the NuExtract3 pilot. It does not evaluate automatic schema generation, visual extraction, production acceptance, or the reserved CORD holdout.

## Locked source and model boundary

The [committed six-source schema lock](../../product_eval/fixtures/gliner25_small_oracle_six.json), SHA256 `1871cf55460944e748257c4e5de8832870250a581158126aba8b90f51ca5e77b`, contains only per-document reference **field IDs and shapes**, source and completed-OCR hashes, and deterministic model settings. It contains no reference values or row content. It reuses the [twelve-source Graph/NuExtract lock](../../product_eval/fixtures/docling_graph_v1_dev_sources.json), SHA256 `61bef64cafb35739eba3a087fe5a742c57e68c340834325a8f77e49f63c5b047`, selecting only the six `role=scored` rows: two VRDU registration, two VRDU ad-buy, and two CORD v2 development receipts. Six source SHA256 and six completed OCR-text SHA256 values are individually pinned in the schema lock; all are checked against the raw files and OCR sidecars before a model call. Gold files are hash-checked in the inventory path, but only the separate `score` command loads values after all model replies are sealed.

The official [GLiNER2.5 Small model card](https://huggingface.co/fastino/gliner2.5-small-v1) describes a 74M-parameter English boundary model, CPU `AutoExtractor`, span offsets, `natural` anchored records, and long-document scanning. Pin model repository revision `df5910e44bc4ffdb0d95399a83b0ca4516349aa5`, `model.safetensors` size **295,567,700 bytes** and SHA256 `4ee982787ace270d4bf15dbcb28ced38e0aa201372347114ceedd6336055de2b` from the official Hub revision metadata. The four required config/tokenizer files were fetched from that revision, checked against its Git blob IDs, and their byte counts and SHA256 values are pinned in the schema lock and runner. The diagnostic pins `gliner2==2.1.0` (PyPI wheel SHA256 `0c242c5de53f37020df835788fc4eb820e1673b5212c202cd90e9234a7e786bc`). The worker must use CPU PyTorch, local model files, and offline Hugging Face flags; every model/config/tokenizer file is checked against its expected byte count and digest before a model call. Report the installed Torch/Transformers versions. No cloud/API call is allowed.

## One frozen supplied-schema arm

Use each document's exact annotated `field_id` and `type` as an intentionally generous oracle schema, without annotated values, source quotes, row ordinals, or family-specific aliases. Map `string` and `array[string]` IDs to GLiNER entity labels. Preserve the different output shapes: a scalar succeeds only if all candidate mentions have one distinct exact string; multiple distinct strings cause abstention; a scalar list retains candidate order. Map all `array[object]` IDs in that document to **one** `line_items` structure with `mode="natural"`, a `required_one` anchor equal to the first linked ID in reference field order, and `optional_one` remaining fields. This is the model's documented [record mode](https://huggingface.co/fastino/gliner2.5-small-v1#structured-records); it preserves row identity rather than later zipping unrelated lists. Missing fields stay missing. Extra model rows remain extra; no matching by annotation values is permitted.

Call `extract_long` once per document with `chunk_size=384` words, `chunk_overlap=64`, spans and confidence enabled, default GLiNER2 overlap/threshold behavior, and four CPU threads. The six OCR inputs range from 238 to 28,836 characters, so a normal context call would truncate the longest document. The [official long-document guidance](https://huggingface.co/fastino/gliner2.5-small-v1#long-documents) states that spans or relations spanning chunks are not stitched. **Do not join partial model rows across chunks**; a missed complete row is a miss. OCR is supplied exactly as the earlier locked page-labeled text, with no image input. The model may see reference names/shapes but never gold values or row ordinals.

The [runner and scorer](../../product_eval/gliner25_small_oracle_diagnostic.py) must be committed before any model inference. The `run` command writes only outside Git, creates a new directory, uses a fresh worker process per source, and seals all six reply hashes in `run.json`. Each worker is capped at 240 seconds, sampled 4 GiB process RSS, 2 GiB remaining host RAM, and a one-source-at-a-time schedule. Preflight requires at least 4 GiB available host RAM and 1 GiB free output storage. A timeout or resource breach aborts subsequent workers; the unattempted sources remain in the six-source scoring denominator. No retry or post-hoc schema/threshold/chunk tuning is allowed in this arm. If the pinned package/API cannot express or execute the declared natural record schema, stop and report incompatibility; do not silently replace it with flattened fields.

## Scoring and evidence

After `run.json` is sealed, run `score` against the unchanged gold files. Reuse the prior NuExtract oracle-value scorer to report exact positive scalar fields, exact scalar-list positives, linked cells at annotation ordinal, and strict order-independent complete rows. A complete row must include every annotated field; one predicted row can match at most one annotated row. Failures and unattempted sources receive empty predictions. Keep each source and family separate, because the earlier NuExtract **13/32 positive scalars and 24/43 complete rows** were highly uneven, with one ad-buy source contributing 21/30 rows and the other 0/6.

For every emitted value with a model span, verify `ocr_text[start:end] == text` at the original OCR character offsets. Report verified, absent, and invalid spans separately. Offsets refer to OCR text, not PDF page geometry; no text offset creates a box automatically. Model outputs with no verified quote/span are still scored as model values but **zero are eligible for automatic acceptance**. This is a text-only, oracle-schema, six-document development diagnostic, so a result cannot be read as end-to-end arbitrary-document quality or cheaper total cost. A product extraction change would still require the user's fresh gate of at least 2,000 distinct-source extractions and a diverse holdout.
