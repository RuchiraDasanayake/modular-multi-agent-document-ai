# Product platform reuse decision, 12 October 2026

This is a focused check of the [infrastructure audit](INFRASTRUCTURE_REUSE_AUDIT_2026-10.md) against the current product code. It changes no runtime behavior. The paper's research services and the experimental `process-auto` product path are distinct. Better persistence will not improve extraction accuracy by itself.

## Decision criteria

Rank options in this order: (1) recover every accepted result and review decision after a crash, with owner isolation; (2) replay an extraction without duplicate terminal results or overwritten candidates, while recording uncertainty about external API calls; (3) sustain measured p95 queue wait, completion time, and throughput at bounded CPU/GPU concurrency; (4) minimize total cost, including backup, restoration, monitoring, and operator effort. A software popularity or benchmark claim is insufficient to replace an existing component.

## What the product actually uses

| Boundary | Observed state | Gap that matters |
| --- | --- | --- |
| Metadata | [`jobs.ts`](../../frontend/src/server/jobs.ts) atomically replaces a job JSON file, but `mutateJob` reads then rewrites it. The unused [Alembic product schema](../../scripts/product_migrations/versions/20261012_0001_product_metadata.py) has owner keys, immutable-event tables, and a unique run idempotency key. | Atomic replacement prevents a torn single file, not simultaneous lost updates or a transaction spanning job, run, and review. The database has no live product writer or tested import. |
| Execution | [`product-auto.ts`](../../frontend/src/server/product-auto.ts) checks for an active run, stages files, writes a running record and lease, then starts a child process. The [private worker](../../idpo/product_auto/worker_server.py) admits one request and returns HTTP 429 when busy; the [client](../../frontend/scripts/product-worker-client.mjs) holds the request for up to six hours. | There is no durable pending state, queue, cancellation, or bounded retry policy. The check and start are not one transaction across frontend instances. The draft `product.runs` table only allows `running`, `success`, and `failed`; it has no enqueue outbox or claim/attempt state. |
| Source and output bytes | The [production Compose file](../../docker-compose.prod.yml) gives frontend and worker one `idpo_data` volume. Run receipts bind source hashes, and the frontend validates candidate/manifest relationships before showing a result. | This is a useful one-host boundary, but not shared multi-host object storage. A metadata commit and filesystem publication cannot be atomic together; recovery must reconcile them. Backup and restore have not been demonstrated. |
| Human review | Product auto review and recipe histories publish numbered files with hard-link compare-and-set in [`product-auto.ts`](../../frontend/src/server/product-auto.ts) and [`product-auto-recipes.ts`](../../frontend/src/server/product-auto-recipes.ts). A separate job review path still overwrites [`review/results.json`](../../frontend/src/server/review.ts). | The product histories reject stale revisions, but events, current job display, and output bytes remain in separate stores. Preserve the immutable candidate and the entire review chain during any import; never infer an owner or revision from an unverified legacy file. |
| Deployed services | [Compose](../../docker-compose.prod.yml) already includes PostgreSQL 16 via `pgvector/pgvector:pg16` and Redis with AOF. Neither holds product job truth today. Both image tags can move within their tag lines. | Pin tested image digests before release and test database/volume restore. Redis AOF alone is not a substitute for authoritative product metadata or a tested backup; [Redis documents its persistence tradeoffs](https://redis.io/docs/latest/management/persistence/). |

## Keep, adapt, replace

**Keep PostgreSQL as the target product metadata store.** Do not add MongoDB, a graph database, or a second vector database for jobs or HITL. The existing migration has a suitable foundation, but it is not a deployed repository. Complete a transactionally scoped writer with optimistic job revisions, an authenticated owner filter on every query, a restricted role, and tested row security. PostgreSQL notes that table owners and privileged roles can bypass [row-level security](https://www.postgresql.org/docs/16/ddl-rowsecurity.html), so policies do not replace API authorization. Add a separate migration for queued/leased/terminal attempts and an enqueue outbox **only when** the queue is implemented. Keep the source hash, candidate hash, model/config versions, reviewer actor, decision, and prior-event link immutable. Publish and verify a hashed artifact before committing a terminal result; reconcile any orphan on recovery. This is an application protocol, not a cross-store transaction.

**Keep the single-host worker for the immediate local quality gate; adapt execution when load requires it.** [Celery with the existing Redis broker](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html) is the preferred multi-worker candidate because the extraction worker is Python and Redis is already deployed. Celery explicitly documents [duplicate execution with late acknowledgements](https://docs.celeryq.dev/en/stable/userguide/tasks.html). The database run key and request fingerprint must therefore deduplicate work, and workers must publish one immutable artifact per attempt. Set finite retries, time/resource limits, concurrency, queue depth, and a measured Redis visibility timeout; long tasks can be redelivered while still running. Add an outbox dispatcher so a committed run request is eventually enqueued even if the process dies between the database commit and broker publish. Redis must be configured and tested for a no-eviction broker workload and recoverable persistence.

| Alternative | Why it is not the next default |
| --- | --- |
| PostgreSQL `FOR UPDATE SKIP LOCKED` queue | [PostgreSQL supports queue-like consumers](https://www.postgresql.org/docs/16/sql-select.html), which would remove the broker dependency. It would also require us to own leasing, retries, scheduling, fairness, and stalled-worker recovery. Reconsider only if a bounded Celery trial shows a real reliability or operating-cost disadvantage. |
| Temporal | [Durable workflow replay](https://docs.temporal.io/workflow-execution) is valuable for long-lived, branching human-wait workflows, but adds a service and a new execution model. The current review is a separately versioned action after a bounded extraction, not evidence that workflow replay is needed. |
| SQLite or a new document database | Neither solves the existing need to share transactional owner-scoped product state across API and workers better than the PostgreSQL service already present. A replacement needs a measured gain in correctness, throughput, or full operating cost. |

**Keep local bytes while one host suffices.** Product run receipts bind source hashes, but current upload filenames are generated IDs, not content addresses, and candidate byte-hash verification is not yet a live product guarantee. Put source and artifacts behind an interface that returns an owner-scoped opaque ID, hash, size, format, and retention policy; never expose paths as authorization. Introduce an object-store backend only when workers no longer share a host, then test put/get/hash, concurrent publication, deletion policy, backup, and restore against the same corpus. [SeaweedFS](https://github.com/seaweedfs/seaweedfs) is an active Apache-2.0 S3-compatible candidate, not an automatic deployment choice. The existing product review UI remains the operator workflow; a labeling package can help build benchmark gold data, but does not replace job ownership and review audit.

## Promotion gates

1. Run the existing migration against a disposable live PostgreSQL instance, then backup and restore it. Test cross-owner access, restricted roles, event trigger immutability, and upgrade retry. The current offline migration test does not establish these properties.
2. Import a copied historical set with source and artifact hashes, owner IDs, and full review/recipe chains; compare read-only file and database views. Freeze writes for the final import. Exercise reverse export before changing the authoritative writer.
3. Test two simultaneous review saves, two identical run requests, one conflicting request with the same idempotency key, worker crash before/after artifact publication, broker redelivery, and late completion after lease expiry. Exactly one terminal result and an intact audit chain must remain.
4. Measure p50/p95 queue wait, completion latency, throughput, retry rate, lost/duplicate attempts, compute/API spend, and reviewer minutes on the same source-locked workload. Keep the simpler path unless the candidate improves the relevant gate without a data-loss or owner-isolation regression. Any later extraction implementation still needs the user's fresh 2,000-distinct-document quality gate; this report is not such an implementation.

No live database migration, queue pilot, Docker execution, or object-store compatibility test was performed for this report. The [existing cutover plan](PRODUCT_METADATA_MIGRATION.md) remains authoritative until those gates pass.
