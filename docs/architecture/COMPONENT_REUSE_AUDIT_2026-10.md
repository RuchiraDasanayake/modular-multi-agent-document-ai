# Component reuse audit, 12 October 2026

Status: implementation decision record. The [current runtime](../SYSTEM_CONTRACT.md),
[target architecture](ADR-0001-evidence-preserving-extraction.md), and
[quality gates](../PRODUCTIZATION_PLAN.md) remain the contracts. A newer package or a vendor benchmark is
not a product accuracy result. The decision criteria, in order, are correct fields and linked rows,
inspectable evidence, total cost per correctly released document, reliability, data rights, and operational
complexity. The available execution modes are local CPU, an 8 GB local GPU, and opt-in cloud APIs.

## Decisions from the code and measurements

| Concern | Reuse decision | Current evidence and next gate |
| --- | --- | --- |
| PDF rendering | **Done:** product scan pages now use pinned `pypdfium2`/PDFium first, with Poppler fallback. Keep native PDF text as a fast path. | This replaces a PyMuPDF dependency with a permissively licensed renderer. The [2,000-source v8 provenance gate](../evaluations/VRDU_2000_NO_MODEL_V8_PROVENANCE.md) verified PDFium rendered all 831 OCR pages, with 4.2423% strict schema F1 and zero linked rows. Renderer provenance is measured; extraction quality did not improve. [pypdfium2](https://github.com/pypdfium2-team/pypdfium2/blob/main/README.md), [PyMuPDF licensing](https://github.com/pymupdf/PyMuPDF). |
| Scan OCR | **Challenge Tesseract; do not treat it as the best engine.** Keep the pinned output as a paired control. Test RapidOCR with PP-OCRv6 detection and recognition on full pages; consider a routed fallback only if downstream correctness improves. | On 1,389 identical creator-annotated CORD development crops, RapidOCR recognized 88.265% exactly versus Tesseract's 52.772%. In a separate 60-receipt full-page pilot, RapidOCR page text exposed 1,311/1,389 annotated strings versus 791/1,389 for Tesseract, but the unchanged extractor mapped **zero** exact CORD scalars or linked rows with either text. It also proposed fewer raw schema fields from RapidOCR text. Do not switch the default based on OCR alone. [crop result](../evaluations/CORD_DEVELOPMENT_TEXT_BOX_OCR_RESULT_20261012.md), [full-page result](../evaluations/CORD_FULL_PAGE_OCR_DEV_RESULT_20261012.md), [RapidOCR model list](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/). |
| Mixed-format conversion | **Benchmark source-native parsers first and keep `docling-slim` as a competing normalizer.** Preserve native table/cell, sheet, slide, DOM and MIME locators rather than inventing page boxes. | On the same five locked synthetic files, [native parsers](../evaluations/MIXED_FORMAT_NATIVE_DEV_RESULT_20261012.md) recovered **45/45** exact known cells and **45/45** resolvable locators. [Docling-slim](../evaluations/DOCLING_MIXED_FORMAT_DEV_RESULT_20261012.md) recovered **36/45**; it missed the EML HTML alternative. Neither has cell pixel boxes or a real-document extraction score. Gate each format on rights-cleared documents, safe parsing and the 2,000-source product run after integration. |
| Tables and reading order | **Try established parsers before writing a row detector.** Keep cell geometry and row/column structure, never flattened Markdown alone. The full PP-StructureV3 CPU profile fails the current free-RAM guard. | On the same 12 frozen PDFs and 219 gold linked rows, [MinerU 4.0.9 Basic](../evaluations/MINERU_4_BASIC_ADBUY12_RESULT_20261012.md) colocated all gold cells of 6 rows with exact text in distinct parser rows, and matched 211/808 exact cells in 229 s. [Docling](../evaluations/VRDU_ADBUY12_TABLE_PARSER_COMPARISON_20261012.md) did so for 3 rows and 279 cells in 538 s; pdfplumber `text` found 4 rows in 10 s. The parser-row metric permits extra cells and does not assign business field IDs. MinerU's narrow row gain and cell regression are insufficient for automatic linked-row acceptance. |
| Hard visual pages | **Reject the tested NuExtract3 blind-schema route; retain it as a conditional value-extraction candidate.** The full PaddleOCR-VL 1.6 parser ran locally but failed the row/evidence gate; keep the generic Qwen3-VL pilot as a negative control. | The pinned [NuExtract3 local development run](../evaluations/NUEXTRACT3_LOCAL_DEV_RESULT_20261012.md) fit the 8 GB GPU and matched 22/53 reference fields but **0/26 linked field pairs** in blind discovery. With the reference schema supplied it matched 13/32 positive scalars and 24/43 exact complete rows on six sources, with strong source-to-source variance and no verified boxes/spans. [PaddleOCR-VL 1.6](../evaluations/PADDLEOCR_VL16_ADBUY12_RESULT_20261012.md) recovered 14/219 permissive parser rows and zero strict exact rows, with no cell coordinates or business field mapping. Neither route supports automatic release. [Qwen pilot](../evaluations/LOCAL_QWEN3_VL_TWO_DOC_V2_PROMPT_PILOT.json). |
| Schema/value generation | **Keep a provider-neutral, two-step contract** and strict result verifier. Use an established constrained-output runtime when a model supports it; do not write a custom JSON decoder. | The no-model 2,000-source gate has 4.2423% strict schema F1 and zero linked rows. Source-locked [Graph/Qwen3-4B](../evaluations/DOCLING_GRAPH_SCHEMA_DEV_RESULT_20261012.md) and [NuExtract3](../evaluations/NUEXTRACT3_LOCAL_DEV_RESULT_20261012.md) development runs both missed all 26 linked field pairs under the frozen alias contract; neither automatic schema route qualifies. A [six-call synthetic ICORE probe](../evaluations/ICORE_BOUNDED_CAPABILITY_20261012.md) showed small strict JSON-schema replies, but the [real-document trial](../evaluations/ICORE_REAL_DEVELOPMENT_SIX_RESULT_20261012.md) stopped at its first transport failure with no usage receipt and cannot rank model quality. Well-formed responses can still assign the wrong meaning or row; keep typed validation and source evidence. |
| Metadata and queue | **Reuse PostgreSQL and Redis already in Compose.** Move product jobs, owners, review/recipe revisions and idempotency into PostgreSQL; use a mature bounded worker queue such as Celery over Redis once the single-host worker smoke passes. | The current frontend file/lease runner has recovery but is not a distributed durable queue. Celery may redeliver late-ack tasks, so immutable source hashes, unique run keys and atomic result publication are required. A queue package cannot supply exactly-once business results on its own. [current recovery](ADR-0004-product-run-recovery.md), [Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html). |
| Original and derived bytes | **Keep content-addressed files on one host; add an S3-compatible storage adapter only when multi-host workers require it.** Keep artifacts separate from transactional metadata. | A new object service adds operational cost without improving the current single-host extraction. The future adapter must enforce owner scope, immutable hashes, retention and backup/restore. PostgreSQL remains the source for job and review state; a vector database is not needed for first-version recipe lookup. |
| Human review and gold labels | **Extend the owner-scoped operator UI for field, table, and evidence correction.** Consider Label Studio for independent gold annotation rather than replacing the product review experience. | The present UI can review values and existing linked cells and add wholly missed scalar fields or linked columns with exact OCR quotes. Optional self-reported active seconds are recorded per save; total reviewer time and adjudicator agreement are not yet measured. [Label Studio](https://github.com/HumanSignal/label-studio) supports task import/export, but integration must pass owner and data-rights checks. |
| Metrics and tracing | **Use OpenTelemetry instrumentation at stage boundaries, plus explicit cost records.** Keep a simple local artifact report until a service deployment needs an external collector. | We have partial stage latency, token and failure metadata, but no priced compute/API ledger or reviewer elapsed time. Trace upload, render, OCR, table parse, schema, values, verification, queue wait, and review by run ID without logging document text or credentials. [OpenTelemetry Python](https://opentelemetry.io/docs/languages/python/instrumentation/). |
| Service topology | **Done:** the default Compose configuration starts only PostgreSQL, Redis, gateway, product worker and frontend. Opt into four legacy research services with `--profile research`. | Those services are not called by `process-auto`; starting them by default increased build/start work and exposed the host to their configured resource limits without contributing to product extraction. Both Compose files resolve in default and research profiles. A live container smoke still requires an available Docker daemon. |
| Agents, skills and memory | **Represent reusable document skills as versioned, reviewed recipes and bounded parser/model tools.** Keep autonomous agent loops and vector retrieval out of the hot path until a paired ablation wins. | The October static-versus-adaptive study did not show an accuracy gain and made receipts slower. Extra autonomous steps increase cost, latency and failure modes; they may still be useful for exceptional pages if measured against the same parser, gold and budget. [decision gate](../PRODUCTIZATION_PLAN.md#ahmn-and-agent-keepremove-gate). |

## Immediate experiment order

1. **Completed:** compare the clean 2,000-unique-source PDFium-first gate with the pinned Tesseract control. The [v8 provenance gate](../evaluations/VRDU_2000_NO_MODEL_V8_PROVENANCE.md) verified that PDFium actually rendered all 831 scanned pages; extraction quality did not improve.
2. **Completed:** Docling and pdfplumber on the same 12 public PDFs. Both failed the exact linked-row gate;
   do not ship either parser as an autonomous table adapter. CORD development-only crop and full-page OCR favor
   PP-OCRv6 for text availability, but the current extractor still returns zero exact mapped fields/rows from
   either engine. Fix schema meaning and row linking before product OCR promotion. Keep reserved CORD sources
   unopened by candidate inference.
3. **Completed:** MinerU 4 Basic passed the resource guard but recovered only 6/219 permissive parser rows. The separate
   NuExtract3 blind-schema run matched 22/53 reference fields and 0/26 linked pairs; its reference-schema value arm
   matched 24/43 complete rows on only six development documents, without evidence verification. The stronger
   [PaddleOCR-VL 1.6 full pipeline](../evaluations/PADDLEOCR_VL16_ADBUY12_RESULT_20261012.md) reached 14/219
   permissive parser rows but zero strict rows and no cell boxes; do not promote it. Freeze an adjudicated
   mixed-format set with table geometry, typed values and source evidence.
   Compare viable parsers on the same pages, with latency, RAM/VRAM and rights.
4. Integrate the smallest measured winner behind the versioned parsed-document contract. Run a fresh 2,000-unique-source
   end-to-end gate after each substantive extraction implementation; report failures and review burden in the denominator.
5. Prove the five-service product stack in a live container, then move job/review metadata to transactional storage
   and a bounded queue. Measure cost per correctly released document before claiming it is cheaper.

The current evidence is strong enough to replace expensive default service startup and to **test** better parsers.
It is not strong enough to claim that a new OCR engine, VLM, queue, or database has already made the extractor
world-class. Promotion requires the paired accuracy, evidence, cost and deployment gates above.

## Broader parser scan and selection order

The parser choice must be made at the **cell and field** level. A Markdown or reading-order benchmark does not
establish that values have the right labels, rows, and source regions. These projects are credible comparators, not
preselected replacements:

| Project | Reusable capability | Deployment or rights constraint | Decision here |
| --- | --- | --- | --- |
| [pdfplumber](https://github.com/jsvine/pdfplumber/blob/stable/README.md) | Native PDF text, geometry, and `find_tables`/`extract_tables` with rows and cells. | Does not OCR scans. The fixed `text` profile colocated the exact gold cells of 4/219 rows in distinct parser rows and emitted 8,548 nonempty cells for 808 gold cells on the [frozen comparison](../evaluations/VRDU_ADBUY12_TABLE_PARSER_COMPARISON_20261012.md). | Keep as a cheap native-PDF triage candidate only; require verified rows, columns and source evidence before any product use. |
| [Microsoft Table Transformer](https://github.com/microsoft/table-transformer/blob/main/docs/INFERENCE.md) | Detects tables and predicts row/column cells with per-cell boxes; official cell-list output preserves more evidence than HTML. | The [local feasibility audit](../evaluations/TATR_ADBUY12_FEASIBILITY_20261012.md) found no product word-box feed: native PDF text lacks it and current scan OCR exposes line polygons. Its official inference code imports AGPL/commercial PyMuPDF, and the upstream repo is archived. No local inference or quality score exists. | Conditional parser-only comparator on the same 12 PDFs after a word-box and coordinate-transform path is verified. Replace the PyMuPDF geometry use and revalidate before any permissive product adapter. |
| [Docling](https://docling-project.github.io/docling/reference/docling_document/) | Versioned document structure and table cell model across PDF and office formats. | CPU conversion took about 538 s across 12 PDFs, colocated the exact gold cells of 3/219 rows, and no complete row in the two pure scans. Extra parser cells are allowed by this metric. | Do not integrate as an automatic linked-row source on this evidence; test stronger specialist on the same hard subset. |
| [PaddleOCR PP-StructureV3](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PP-StructureV3.html) | Document layout and table recognition in one supported pipeline. | The prepared full CPU profile has a 15.5–17.7 GB estimated process peak and fails the current free-RAM guard; the 8 GB card has not been proven sufficient. The separate [PaddleOCR-VL 1.6 result](../evaluations/PADDLEOCR_VL16_ADBUY12_RESULT_20261012.md) does not test PP-StructureV3. | Keep the source-locked preparation; run only when a safe host or smaller proven profile is available. |
| [Marker](https://github.com/datalab-to/marker) and [Surya](https://github.com/datalab-to/surya) | Marker emits JSON blocks and table HTML/boxes; Surya 2 exposes OCR, layout and table recognition from one roughly 650M-parameter VLM. | Code is Apache-2.0, but the model weights have [additional commercial terms](https://github.com/datalab-to/surya/blob/master/MODEL_LICENSE). Their current GPU route expects vLLM in Docker; a CPU route uses llama.cpp. Neither local fit nor extraction accuracy is established here. The author's olmOCR score measures parsing, not our field/row accuracy. | Keep as a bounded comparator if the Apache-licensed Paddle path leaves a quality gap; check exact weight terms and runtime before promotion. |
| [MinerU 4](https://opendatalab.github.io/MinerU/) | Multiple input formats and a [versioned structured result](https://opendatalab.github.io/MinerU/reference/output_files/) with Basic CPU OCR/table models and Standard VLM tier. | Its [custom license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md) adds commercial-scale thresholds and attribution for online services; do not label it plain Apache-2.0. Standard's 8 GB GPU fit is only a planning assumption, not a guarantee. | Pinned Basic pilot completed [12/12 parses but only 6/219 exact rows](../evaluations/MINERU_4_BASIC_ADBUY12_RESULT_20261012.md); retain as a measured control, not a product default. |
| [Unstructured OSS](https://github.com/Unstructured-IO/unstructured) | Broad input partitioning and a `hi_res` PDF table path; HTML can preserve table rows/cells. | `auto` selects fast native text or OCR-only for some PDFs; `hi_res` requires extra inference dependencies, and fallback can change the actual strategy. See its [strategy code](https://github.com/Unstructured-IO/unstructured/blob/main/unstructured/partition/strategies.py). | Useful file-format adapter candidate, but verify the effective strategy and score cells before using it as a table engine. |

The next promotion decision is therefore a **measured routing rule**: native text/table extraction when reliable,
specialist OCR/layout on scans or broken tables, and an expensive visual model only for pages that still fail. All
branches must yield the same versioned parsed-document and source-evidence contract, and failures must remain in the
reported denominator. A package's own aggregate score, especially one for Markdown, cannot replace this product gate.
