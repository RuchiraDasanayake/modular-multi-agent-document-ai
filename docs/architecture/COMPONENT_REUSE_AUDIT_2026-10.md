# Component reuse audit, 12 October 2026

Status: implementation decision record. The [current runtime](../SYSTEM_CONTRACT.md),
[target architecture](ADR-0001-evidence-preserving-extraction.md), and
[quality gates](../PRODUCTIZATION_PLAN.md) remain the contracts. A newer package or a vendor benchmark is
not a product accuracy result. The decision criteria, in order, are correct fields and linked rows,
inspectable evidence, total cost per correctly released document, reliability, data rights, and operational
complexity. The available execution modes are local CPU, an 8 GB local GPU, and opt-in cloud APIs.

## Decisions from the code and measurements

| Concern | Reuse decision | Current evidence and next gate |
| --- | --- | --- |
| PDF rendering | **Done:** product scan pages now use pinned `pypdfium2`/PDFium first, with Poppler fallback. Keep native PDF text as a fast path. | This replaces a PyMuPDF dependency with a permissively licensed renderer; three-page pixel/text checks passed. The new 2,000-source PDFium-first gate is running. Add per-page renderer and fallback provenance before claiming every page used PDFium. [pypdfium2](https://github.com/pypdfium2-team/pypdfium2/blob/main/README.md), [PyMuPDF licensing](https://github.com/pymupdf/PyMuPDF). |
| Scan OCR | **Challenge Tesseract; do not treat it as the best engine.** Keep the pinned output as a paired control. Run RapidOCR with PP-OCRv6 small/medium on the same scanned pages and consider a routed fallback only if downstream correctness improves. | On 30 selected VRDU scan pages, PP-OCRv6 small exposed 121/146 page-local target strings versus 107/146 for the existing Tesseract text, with higher CPU time and memory. This is a text-presence proxy, not field F1. A separate CORD development crop diagnostic is frozen; neither result alone justifies a default switch. [pilot](../evaluations/RAPIDOCR_PPOCRV6_THIRTY_SCAN_PILOT.md), [PaddleOCR release](https://github.com/PaddlePaddle/PaddleOCR/releases/tag/v3.7.0), [RapidOCR model list](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/). |
| Tables and reading order | **Try established parsers before writing a row detector.** First compare Docling TableFormer on frozen public PDFs; then challenge failed scan/table slices with PP-StructureV3. Use their cell geometry and row/column structure, never flattened Markdown alone. | A ten-PDF Docling conversion smoke succeeded, but one scan table collapsed and native-PDF CPU median was 30.17 s versus 0.119 s for the cheap intake on seven timed PDFs. The 12-PDF cell/row diagnostic is staged. [Docling document model](https://docling-project.github.io/docling/reference/docling_document/), [Docling model catalog](https://github.com/docling-project/docling/blob/main/docs/usage/model_catalog.md), [PP-StructureV3 output](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-StructureV3.en.md). |
| Hard visual pages | **Evaluate specialist document VLMs as bounded fallbacks**, especially PaddleOCR-VL 1.6; keep the general Qwen3-VL pilot as a negative control. | Local Qwen3-VL Q4 ran on the 8 GB GPU but matched only 1/19 gold scalars on two schema-supplied public PDFs and no linked cells. No specialist VLM has cleared our field, row, evidence, or cost gate. Test exact model weights, VRAM peak, output structure and source-region verification. [Qwen pilot](../evaluations/LOCAL_QWEN3_VL_TWO_DOC_V2_PROMPT_PILOT.json), [PaddleOCR-VL model card](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6). |
| Schema/value generation | **Keep a provider-neutral, two-step contract** and strict result verifier. Use an established constrained-output runtime when a model supports it; do not write a custom JSON decoder. | The no-model 2,000-source gate has 4.245% strict schema F1 and zero linked cells; local Qwen and ICORE public-PDF pilots have not shown reliable real-document extraction. `llama.cpp` and vLLM document grammar/JSON-schema support, but even a well-formed response can assign the wrong meaning or row. Probe enforcement on each pinned server version; keep typed validation and source evidence. [llama.cpp grammars](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md), [v6 gate](../evaluations/VRDU_2000_NO_MODEL_V6.md). |
| Metadata and queue | **Reuse PostgreSQL and Redis already in Compose.** Move product jobs, owners, review/recipe revisions and idempotency into PostgreSQL; use a mature bounded worker queue such as Celery over Redis once the single-host worker smoke passes. | The current frontend file/lease runner has recovery but is not a distributed durable queue. Celery may redeliver late-ack tasks, so immutable source hashes, unique run keys and atomic result publication are required. A queue package cannot supply exactly-once business results on its own. [current recovery](ADR-0004-product-run-recovery.md), [Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html). |
| Original and derived bytes | **Keep content-addressed files on one host; add an S3-compatible storage adapter only when multi-host workers require it.** Keep artifacts separate from transactional metadata. | A new object service adds operational cost without improving the current single-host extraction. The future adapter must enforce owner scope, immutable hashes, retention and backup/restore. PostgreSQL remains the source for job and review state; a vector database is not needed for first-version recipe lookup. |
| Human review and gold labels | **Extend the owner-scoped operator UI for field, table, and evidence correction.** Consider Label Studio for independent gold annotation rather than replacing the product review experience. | The present UI can review values and existing linked cells; work to add wholly missed columns is in progress. Reviewer minutes and adjudicator agreement are not yet measured. [Label Studio](https://github.com/HumanSignal/label-studio) supports task import/export, but integration must pass owner and data-rights checks. |
| Metrics and tracing | **Use OpenTelemetry instrumentation at stage boundaries, plus explicit cost records.** Keep a simple local artifact report until a service deployment needs an external collector. | We have partial stage latency, token and failure metadata, but no priced compute/API ledger or reviewer elapsed time. Trace upload, render, OCR, table parse, schema, values, verification, queue wait, and review by run ID without logging document text or credentials. [OpenTelemetry Python](https://opentelemetry.io/docs/languages/python/instrumentation/). |
| Service topology | **Done:** the default Compose configuration starts only PostgreSQL, Redis, gateway, product worker and frontend. Opt into four legacy research services with `--profile research`. | Those services are not called by `process-auto`; starting them by default increased build/start work and exposed the host to their configured resource limits without contributing to product extraction. Both Compose files resolve in default and research profiles. A live container smoke still requires an available Docker daemon. |
| Agents, skills and memory | **Represent reusable document skills as versioned, reviewed recipes and bounded parser/model tools.** Keep autonomous agent loops and vector retrieval out of the hot path until a paired ablation wins. | The October static-versus-adaptive study did not show an accuracy gain and made receipts slower. Extra autonomous steps increase cost, latency and failure modes; they may still be useful for exceptional pages if measured against the same parser, gold and budget. [decision gate](../PRODUCTIZATION_PLAN.md#ahmn-and-agent-keepremove-gate). |

## Immediate experiment order

1. Finish the clean 2,000-unique-source PDFium-first gate and compare it with the pinned Tesseract control.
2. Complete the Docling 12-PDF cell/row diagnostic and the CORD development-only OCR challenge; keep the
   reserved CORD sources unopened by candidate inference.
3. Freeze an adjudicated mixed-format set with table geometry, typed values and source evidence. Compare
   Docling, PP-StructureV3 and the specialist VLM on the same hard pages, with latency, RAM/VRAM and rights.
4. Integrate the smallest winner behind the versioned parsed-document contract. Run a fresh 2,000-unique-source
   end-to-end gate after each substantive extraction implementation; report failures and review burden in the denominator.
5. Prove the five-service product stack in a live container, then move job/review metadata to transactional storage
   and a bounded queue. Measure cost per correctly released document before claiming it is cheaper.

The current evidence is strong enough to replace expensive default service startup and to **test** better parsers.
It is not strong enough to claim that a new OCR engine, VLM, queue, or database has already made the extractor
world-class. Promotion requires the paired accuracy, evidence, cost and deployment gates above.

## Broader parser scan and selection order

The parser choice must be made at the **cell and field** level. A Markdown or reading-order benchmark does not
establish that values have the right labels, rows, and source regions. These projects are credible comparators, not
preselected replacements:

| Project | Reusable capability | Deployment or rights constraint | Decision here |
| --- | --- | --- | --- |
| [pdfplumber](https://github.com/jsvine/pdfplumber/blob/stable/README.md) | Native PDF text, geometry, and `find_tables`/`extract_tables` with rows and cells. | Does not OCR scans. Its MIT-licensed, text-layer path should be much cheaper than a vision parser when the source PDF is sound; measure rather than assume the size of that gain. | Run a frozen native-PDF comparator with predeclared `lines` and `text` settings after the Docling diagnostic. Count scans as failed/no-table outcomes. |
| [Docling](https://docling-project.github.io/docling/reference/docling_document/) | Versioned document structure and table cell model across PDF and office formats. | CPU conversion was already much slower than the cheap intake on a small native-PDF smoke. | Finish the 12-PDF exact cell/linked-row diagnostic before product integration. |
| [PaddleOCR PP-StructureV3](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PP-StructureV3.html) | Document layout and table recognition in one supported pipeline. | The official pipeline's model and memory requirements need a local CPU/GPU feasibility check; an 8 GB card has not been proven sufficient. | Compare only on the frozen hard subset where the cheaper parsers fail. |
| [Marker](https://github.com/datalab-to/marker) and [Surya](https://github.com/datalab-to/surya) | Marker emits JSON blocks and table HTML/boxes; Surya 2 exposes OCR, layout and table recognition from one VLM. | Code is Apache-2.0, but the model weights have [additional commercial terms](https://github.com/datalab-to/marker/blob/master/MODEL_LICENSE). Their current GPU route expects vLLM in Docker; a CPU route uses llama.cpp. Neither local fit nor extraction accuracy is established here. | Keep as a bounded comparator if Docling/Paddle results leave a quality gap; check the exact weight terms and runtime before promotion. |
| [MinerU](https://github.com/opendatalab/mineru) | Multi-format document parsing with Markdown/JSON and advanced table handling. | Its [custom license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md) adds commercial-scale thresholds and attribution for online services; do not label it plain Apache-2.0. | Consider only after a pinned version, output-geometry, resource and rights audit. |
| [Unstructured OSS](https://github.com/Unstructured-IO/unstructured) | Broad input partitioning and a `hi_res` PDF table path; HTML can preserve table rows/cells. | `auto` selects fast native text or OCR-only for some PDFs; `hi_res` requires extra inference dependencies, and fallback can change the actual strategy. See its [strategy code](https://github.com/Unstructured-IO/unstructured/blob/main/unstructured/partition/strategies.py). | Useful file-format adapter candidate, but verify the effective strategy and score cells before using it as a table engine. |

The next promotion decision is therefore a **measured routing rule**: native text/table extraction when reliable,
specialist OCR/layout on scans or broken tables, and an expensive visual model only for pages that still fail. All
branches must yield the same versioned parsed-document and source-evidence contract, and failures must remain in the
reported denominator. A package's own aggregate score, especially one for Markdown, cannot replace this product gate.
