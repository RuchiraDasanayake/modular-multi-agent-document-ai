# Reuse frontier for product extraction, 12 October 2026

**Decision:** reuse an established parser or extraction component only at a measured boundary. Prioritize schema induction and linked rows, since these dominate the observed quality gap. Keep the existing source-evidence and human-review contract as the acceptance boundary. This is a research and integration decision, not a claim that any new package improves the product.

## What the repository actually does

`process-auto` accepts PDF, common raster images, TXT and its existing JSON input; it does **not** accept DOCX, XLSX, PPTX, HTML or email. It caps an input at 20 MiB, 50 pages and 24,000 characters sent to a model. The product path uses PDF native text/PDFium, Tesseract by default, then either a label/value heuristic or two chat calls for schema and values. The only product chat adapter asks for JSON in the prompt; it does not send a constrained output schema. The value verifier checks typed values and exact OCR quotes, but its candidate representation has text offsets rather than page geometry. Approved recipes do not yet feed extraction. See [`workflow.py`](../../idpo/product_auto/workflow.py), [`logic.py`](../../idpo/product_auto/logic.py), [`provider.py`](../../idpo/product_auto/provider.py) and the [system contract](../SYSTEM_CONTRACT.md).

The execution work is real but does not establish extraction quality. The source-verified [2,000-PDF v8 run](../evaluations/VRDU_2000_NO_MODEL_V8_PROVENANCE.md) covered only registration and ad-buy forms: strict schema F1 **4.2423%**, zero accepted-value F1 and zero proposed linked rows against 7,234 annotated rows. The separate [60-receipt CORD development run](../evaluations/CORD_DEVELOPMENT_NO_MODEL_V1.md) had zero exact proposals for 195 summary values, 458 menu cells and 157 complete menu rows. These are different dataset/scorer contracts; neither measures “any document.” With gold schema supplied, the local 4B [12-PDF pilot](../evaluations/LOCAL_QWEN_ORACLE_SCHEMA_VRDU_TWELVE_PILOT.json) matched 11/98 scalars and 0/111 rows. Better OCR alone cannot close the schema and row gap.

## Concrete component decisions

| Boundary | Decision and reason | Promotion test |
| --- | --- | --- |
| **Automatic schema induction** | **Test [Docling Graph v1.9.1](https://github.com/docling-project/docling-graph/releases/tag/v1.9.1) before growing our own prompt/agent framework.** Its [document-to-template generator](https://github.com/docling-project/docling-graph#generating-a-template-from-documents) converts examples with Docling, proposes classes/fields/relationships as structured data, writes an editable SPEC YAML, and deterministically renders a Pydantic template. This is the closest located OSS match to reusable AI-generated schemas and nested entities. It is MIT-licensed [source](https://github.com/docling-project/docling-graph/blob/v1.9.1/LICENSE). A template still encodes a task/family and needs review; it is not proof that arbitrary one-off documents will induce useful schemas. | In an isolated, pinned environment, compare generated field meaning, type and repeated grouping against adjudicated gold on **unseen** documents/layouts. Test both one-document induction and a reviewed, reusable family recipe. Save the SPEC and template hash; never use gold labels in prompts or auto-approve a generated template. |
| **Graph extraction and source evidence** | **Test, do not replace the verifier.** Docling Graph supports direct and dense extraction through local or remote model backends. Its [provenance ledger](https://github.com/docling-project/docling-graph/blob/v1.9.1/docs/fundamentals/graph-management/provenance.md) deterministically links entities to chunks/pages and sometimes verbatim identifier spans. In direct mode a missing identifier falls back to document scope; dense mode can retain a chunk observation. Neither is a demonstrated exact quote/box for **every** scalar and table cell. | Score each value and linked cell after adapting to our candidate contract. Preserve raw/normalized values and exact source quote or region; send ungrounded and wrong-row results to review. Count all fallback-to-document anchors, hallucinated links, calls and tokens. |
| **Typed extraction from page images** | **Test [Docling `DocumentExtractor`](https://github.com/docling-project/docling/blob/main/docling/.agents/skills/docling/references/extraction.md) as a bounded specialist.** Its documented API accepts a dict or Pydantic template, extracts per-page typed data and reports per-page errors. The feature is explicitly beta and needs a supplied template; it does not itself solve schema induction or our cell-level evidence requirement. Its NuExtract 2.0 2B [model card](https://huggingface.co/numind/NuExtract-2.0-2B) describes a small multimodal extraction model with MIT weights, subject to exact revision/license verification. | Run only after a reviewed/generated schema is frozen. Compare exact fields, linked rows, page/box evidence, GPU memory, latency and cost against the current model route on the same source hashes. Do not infer quality from the model-card benchmark. |
| **Mixed-file intake** | **Test Docling as a format adapter, not as the default PDF/table engine.** Its [supported-format list](https://github.com/docling-project/docling/blob/main/docs/usage/supported_formats.md) includes Office, HTML, CSV and email as well as PDF/images, while its [document model](https://docling-project.github.io/docling/reference/docling_document/) keeps text/table cells and provenance where available. This is a better starting point than implementing each converter. However our [paired 12-PDF table diagnostic](../evaluations/VRDU_ADBUY12_TABLE_PARSER_COMPARISON_20261012.md) found only **3/219** exact complete rows with Docling at 538 s total; that excludes automatic linked-row promotion. | Freeze a small rights-cleared DOCX/XLSX/PPTX/HTML/EML set with expected values, table rows, page or sheet coordinates, failures and resource limits. Verify files with no geometry explicitly disclose that limit. Admit each type individually after conversion, evidence and security checks; do not claim literally every file type. |
| **Hard tables/scans** | Continue the already prepared [PP-StructureV3](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-StructureV3.en.md) 12-PDF challenge after the current CORD OCR diagnostic. It exposes table cell boxes, HTML and OCR text/scores; its full GPU profile exceeds the local 8 GB card per the [feasibility note](../evaluations/PPSTRUCTURE_V3_CPU_PREPARATION_20261012.md). Existing Docling/pdfplumber pilots are negative controls, not product adapters. | Keep all 219 gold rows, including two image-only PDFs, in the denominator. Score complete rows and cells with field labels and evidence after any candidate passes the parser-only check. Promote only if quality gain survives latency/RAM and failure limits. |
| **Broad OCR or KIE bundles** | Keep the paired Tesseract/RapidOCR result as an OCR diagnostic. [PP-ChatOCRv4](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-ChatOCRv4.md) is an established multimodule KIE pipeline, but its documented call requests specified **keys** and may use a remote LLM/MLLM; it is not an automatic schema or free end-to-end answer. [Unstructured `auto`](https://github.com/Unstructured-IO/unstructured/blob/main/unstructured/partition/strategies.py) may silently select native text, OCR-only or high-resolution paths and fall back when optional dependencies are absent. Defer both until the smaller candidates fail a stated slice. | Require actual engine/module provenance, exact weight rights, source-locked field/row gains and priced end-to-end cost. |
| **State, routing and agents** | Reuse the existing PostgreSQL and Redis services for transactional product state and a bounded queue when product job migration is ready; another database, vector index or autonomous agent loop has no demonstrated extraction benefit. Implement routing as a small, observable rule over native text presence, scan quality, table need and prior failures. Keep reusable “skills” as versioned, reviewed extraction recipes, not executable prompts from a document. See [architecture contract](ADR-0001-evidence-preserving-extraction.md) and [component audit](COMPONENT_REUSE_AUDIT_2026-10.md). | Measure the same documents and total review-adjusted cost with and without each route. Preserve tenant scope, idempotent retries and a holdout for recipe changes. |

## Affordable pilot sequence and stopping rules

1. **Finish the already locked CORD text-box OCR challenge.** Keep the 40 reserved CORD receipts unopened by candidate inference. Compare downstream field and row ceilings, not just text coverage. Do not swap OCR merely because it finds more strings.
2. **Finish PP-StructureV3 on the frozen 12 ad-buy PDFs** under the prepared process memory/free-RAM guard. This tests whether an established table engine improves the observed 3–4/219 exact-row parser ceiling. If it does not materially improve complete rows, stop before product integration or a 2,000-source rerun.
3. **Pilot Docling Graph schema induction before adding product agent logic.** Freeze 12 source-hash-selected VRDU PDFs (six per family) and 12 of the 60 CORD development images; keep separate example and scored source IDs. Use a pinned local model or an explicitly capped ICORE allowance after provider reliability/spend is known. Bound generator/extractor calls, output tokens and retries. Save exact package/model/source hashes and every failure. Run per-document zero-shot schema and recipe-from-examples as distinct arms. Compare against the current two-call path with the same gold and a model-eligible denominator; do not call a schema-supplied arm zero-shot.
4. **Only if the schema candidate improves meaning and grouping, challenge value extraction** with Docling Graph direct/dense and Docling `DocumentExtractor` on the same scored sources. Compare correct scalar values, cell labels and row links; exact source evidence; reviewer corrections/minutes; p50/p95 latency; CPU/GPU and API usage. Use [DocILE's KILE/LIR evaluator](https://github.com/rossumai/docile) as an external-format cross-check for localized fields and line-item grouping. Our score remains necessary for newly induced field meaning, abstention, critical errors and cost. The official [VRDU evaluator](https://github.com/google-research-datasets/vrdu#evaluation-tools) provides a second known-schema comparison; neither benchmark scorer alone measures useful automatic schema induction.
5. **Then test new file formats through Docling on a small frozen mixed-format set.** For any implemented extractor/parser/format change, run a fresh ≥2,000 **distinct-source** execution gate and a disjoint diverse holdout. Report schema F1, exact values, linked rows, source correctness, auto-release precision, failures, review time and cost per correctly released document by family. A 2,000-run gate on the two VRDU families cannot substitute for the diverse holdout.

This order spends local CPU and already cached assets first, uses expensive VLM/API calls only on a bounded failing slice, and turns a package into a product dependency only after it beats the current route on the metric the user actually cares about: correct, reviewable structured extraction per total cost.
