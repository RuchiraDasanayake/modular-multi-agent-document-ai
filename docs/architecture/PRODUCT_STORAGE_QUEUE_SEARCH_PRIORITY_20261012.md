# Product storage, queue, and search reuse: implementation priority

**Decision, 12 October 2026; code-status correction, 13 October 2026.** Reuse the PostgreSQL and Redis already deployed for authentication and research, but do not promote their mere presence into a product capability. The immediate extraction blocker is schema meaning and linked rows. The earlier source-verified 2,000-PDF run proposed **zero of 7,234** gold linked rows and had **4.2423%** strict schema F1; its 831 OCR pages completed without timeout ([v8 receipt](../evaluations/VRDU_2000_NO_MODEL_V8_PROVENANCE.md)). The later [mixed 2,000-source run](../evaluations/MIXED_VRDU_CORD_TRAIN_2000_NO_MODEL_RESULT_20261013.md) also proposed zero linked rows. A database or broker cannot repair those outputs. Select storage and execution components on integrity, owner isolation, measured throughput, full operating cost, and ease of recovery; select extraction components on field/row/evidence quality and cost per correctly reviewed document.

## Reuse sequence

1. **First make existing PostgreSQL authoritative for product metadata, with no new database.** Complete the existing migration plan: live upgrade/restore, restricted product role, explicit owner filters and tested row security, immutable candidate and review references, optimistic job revision, and source/artifact SHA checks. PostgreSQL table owners and `BYPASSRLS` roles can bypass row security, so API authorization and role tests remain mandatory ([PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)). Keep document and result bytes on the shared volume until a measured multi-host deployment requires object storage. This preserves cheap local operation and avoids a second storage service.
2. **Then add an outbox and bounded Python workers if admission or one-host throughput is a measured bottleneck.** The present product migration is not a queue schema. Add queued/claimed/attempt records and a transactionally inserted outbox; dispatch only a run ID and owner-scoped lookup key, never document content or credentials. Celery with the existing Redis broker is the first established candidate, not an unconditional switch. Its documented late acknowledgements and Redis visibility timeout can redeliver work, so require a unique request fingerprint, immutable attempt output, one terminal database publication, finite retries, and a policy that never blindly retries an ambiguous paid model call ([Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html), [Redis transport](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html)). Use a dedicated broker database or prefix; test persistence, no eviction, worker loss, duplicate delivery, and latency. PostgreSQL `SKIP LOCKED` is the fallback if a measured Celery pilot has worse full cost or reliability, but it makes this team own leases, scheduling, and stalled-worker recovery ([PostgreSQL 16](https://www.postgresql.org/docs/16/sql-select.html)).
3. **For product search, start with exact owner/family/state lookup and approved recipe version, then test lexical matching.** The existing composite owner and creation indexes suit job/run lists; add query-specific B-tree indexes only after `EXPLAIN (ANALYZE, BUFFERS)` on a realistic populated database shows a slow query. If reviewed recipe names/labels need fuzzy lookup, PostgreSQL's built-in full-text search or `pg_trgm` can be tested without operating another search server ([text search](https://www.postgresql.org/docs/16/textsearch-tables.html), [`pg_trgm`](https://www.postgresql.org/docs/16/pgtrgm.html)). Require owner filtering before ranking. Do not add OpenSearch, Elasticsearch, a graph store, or vector search for the current tiny, inactive recipe corpus. Even the already installed pgvector project advises trying an exact filter index first; approximate HNSW search applies filters after index scans and can return fewer matches unless tuned ([pgvector](https://github.com/pgvector/pgvector#filtering)). Vector retrieval becomes relevant only if approved-recipe routing beats exact/lexical matching on source-disjoint families and false-route cost, with an owner-isolation and recall test.

## Promotion and stop gates

| Gate | Required evidence before a production switch |
| --- | --- |
| Product DB | Live migration and backup/restore; import comparison by owner, source hash, result hash, review and recipe chain; two simultaneous edits yield one committed revision and one conflict; reverse export succeeds before file-writer retirement. Offline SQL rendering alone is insufficient. |
| Queue | Crash before/after artifact publish, broker outage, redelivery, long task/lease expiry, duplicate request, and ambiguous cloud response leave one terminal result and no silently repeated paid call. Compare p50/p95 queue wait, throughput, failed attempts, CPU/GPU use and operator burden against the one-slot worker on the **same source-locked load**. |
| Search/routing | Predeclare correct recipe top-1/top-k, wrong-recipe critical-field errors, abstention, row and evidence accuracy, reviewer minutes, and total cost per correctly accepted document. Compare exact lookup, lexical, and any vector candidate on held-out families. If no quality/cost win, stop at exact lookup. |
| Overall extraction | Any substantive production extraction route or parser change triggers the user's fresh **at least 2,000 distinct raw-source document** end-to-end gate plus a diverse holdout. The prior 2,000 PDFs cover only two related families and cannot establish arbitrary-document support. |

**Unverified here:** no Docker daemon, live PostgreSQL migration, queue trial, search index benchmark, or restore test was run in this audit. This decision narrows the next experiments; it is not a claim of improved extraction or scaling.
